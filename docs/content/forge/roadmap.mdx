# Roadmap and open questions

<Callout type="warning">Draft proposal, part of Signet 2.</Callout>

## Proposed roadmap

| # | Step | Outcome |
|---|---|---|
| 1 | Publish version 0 of the vocabulary (~15 intents) and of the catalog (~15 archetypes) | A stable list to discuss |
| 2 | Add capabilities to the protocol greeting, as an optional field | Compatible with Signet/1 |
| 3 | Define the translation profile format and the calibration wizard | Tiers 0 and 1 without AI |
| 4 | Prototype without AI: `weapon.ranged` → bow in the Minecraft translator | End-to-end demonstration |
| 5 | 30-case experiment: hand-written rules vs text similarity vs contrastive model | Decide whether the model adds value |
| 6 | First version of Signet Forge (review, pin, export data) | A tool for the community |

## Priority for the first implementation (review-branch proposal)

We are not arguing to delay Forge. We are arguing to freeze the semantic contract before independent translators are built against it, so the model does not become the place where undefined protocol semantics are decided by accident.

- **P0 — semantic/determinism (blocking):** versioned semantic identity; small core plus modular profiles; capability offers that resolve to a deterministic negotiated session contract; explicit required/optional semantics and typed fallback; semantic acceptability separated from session preference; deterministic optional-profile activation; profile authority classes; publisher baseline plus participant overlay; resolver `NO_MATCH` / `ABSTAIN`; deterministic composition/canonicalization; executable conformance vectors.
- **P1 — evidence boundaries (secondary):** mapping provenance and freshness; effective-profile identity; integration mode and declared-versus-enforced permission as separate evidence scopes.
- **P2+ — future-facing (non-blocking):** richer package/update trust distribution; lifecycle and revocation; ecosystem governance; larger validation registries.

A useful first joint experiment is deliberately small: 5–8 intents, 4–6 archetypes, explicit negotiation, one optional profile, one typed fallback and two materially different integration modes. Either outcome is useful: two independently developed implementations derive the same contract, or they disagree in a way that exposes exactly what the semantic contract failed to specify.

See [Semantic contracts](/proposals/semantic-contracts/) and [Translator trust and validation](/proposals/translator-trust-and-validation/).

## Open questions

- What is the minimum a motion profile must measure?
- How do we measure it in a game that does not report its position?
- Who maintains the vocabulary and the catalog, and how are new entries accepted? (See [governance](https://github.com/kian-cx/signetprotocol/blob/main/GOVERNANCE.md).)
- Where does the model run: on the player's machine, on a shared service, or only in Signet Forge?
- How are conflicting community profiles for the same game resolved?

**Review-branch note:** [Semantic contracts](/proposals/semantic-contracts/) proposes answers for identity, negotiation, authority and composition; [Translator trust and validation](/proposals/translator-trust-and-validation/) covers freshness, resolver abstention and the future lifecycle work. The resolver should stay local by default and never be required in the deterministic per-tick path.

Have an answer or a different idea? Open a [discussion](https://github.com/kian-cx/signetprotocol/discussions) or an issue with the `protocol` label.
